# 上下文管理器 · Context Studio

Alife 的上下文管理插件（`Marisa.ContextManager`）。它把「这一次请求到底发了什么给模型」摊开给你看，
并让你像编辑配方一样改它 —— 角色卡、酒馆预设、世界书、长期记忆、对话历史、便签、技能，
全都在一个界面里按发送顺序排好，随时预览、保存、应用。

> 想改代码 / 看每一轮改了什么，见 [CHANGELOG.md](CHANGELOG.md)（按轮次累积的开发记录）。

---

## 它解决什么问题

Alife 原生把角色设定、记忆、历史、便签等拼成一段上下文发给模型，但**拼装过程是黑盒**：
你不知道这一段为什么在这里、那一条为什么没进去，也没法只调其中一块。

这个插件把黑盒拆开：**每一条参与装配的内容都是一个「模块」**，能看、能改、能开关、能调顺序，
改完立刻能看到「这次请求会发什么」，并且可以只对当前角色生效，随时关掉回到原生。

---

## 安装与打开

把整个插件目录放到 `Alife/Storage/Plugins/Marisa.ContextManager/`，重载插件即可
（编译产物会自动落到 `Runtime/PluginContext/CompiledPlugins/`，不需要手工拷 DLL）。

打开方式：插件列表 → 分类 **Marisa** → **上下文管理器** → 打开窗口。

## 界面导览

左侧是七个页面：

| 页面 | 干什么 |
| --- | --- |
| **角色管理** | 选择要管理的角色；同一时刻只有一个角色被完整加载，切换会释放上一个的上下文 |
| **对话测试** | 在当前上下文里跟角色对话，用来验证「这样配之后模型会怎么回」 |
| **上下文装配** | 主战场。按发送顺序列出全部模块，可增删改、调区域与顺序、勾选是否参与装配 |
| **角色预设** | 给每个角色存一份上下文记录（覆盖方式 + 全部模块），随时读取、一键生效、导出带走 |
| **长期记忆** | 查看 MemoryService 压缩出来的分层记忆与事实 |
| **角色附件** | 按角色查看存储的图片、音频、文件引用 |
| **酒馆兼容** | 导入酒馆角色卡（JSON / PNG）、世界书、预设配方，并配置导入策略 |

「上下文装配」里单击模块 → 右侧栏编辑；双击或点「编辑」→ 打开大窗口，内容区块旁还有「⤢ 放大」
可以把正文顶到整个窗口。

## 三种覆盖方式（先搞清这个）

装配页控制栏的「覆盖方式」决定改动**写到哪**：

| 方式 | 含义 | 代价 |
| --- | --- | --- |
| **关闭** | 走 Alife 原生装配，插件不介入 | 无 |
| **插件覆盖**（默认推荐） | 只在每次请求前把上下文重排一遍，**不动角色文件**；改完点「保存草稿」就生效，随时能关 | 插件没启动时不生效 |
| **本地覆盖** | 把装配结果直接写进该角色 `index.json` 的 `Prompt`，**插件关掉也照样生效** | 每改一次都要重新点「应用到当前角色」；想撤回要用「还原原始设定」 |

选「插件覆盖」时，该角色保存的计划会在插件加载 / 角色激活时**自动侧装**，直接对话即可生效，
不需要每次手动点「应用到当前角色」。

## 配置界面

### 一、框架的「插件配置」面板

Alife 会按插件声明自动生成一个配置面板（插件列表里这一项的设置入口）。这里只有 **5 个真的生效的开关**：

| 项 | 默认 | 作用 |
| --- | --- | --- |
| `OverrideMode` | `Off` | 覆盖方式，与装配页那个下拉框是同一个值，两边同步 |
| `ActivePreset` | 空 | 当前选中的酒馆预设名（对应 `ContextManager/Presets/<名>.json`） |
| `UseCharacterCard` | 开 | 是否把角色卡字段（描述 / 性格 / 场景 / 对话示例 / 系统指令 / 历史后指令）并入系统消息层 |
| `UseWorldBook` | 开 | 是否把世界书常驻段并入系统消息层 |
| `ApplyMacros` | 开 | 渲染时是否执行 Handlebars 宏替换；关掉就按原文发送 |

> 之前这个面板里还挂着 `IncludeMemoryHistory`、`IncludeNotes`、`IncludeSkills`、`IncludeGroupChat`、
> `MaxHistoryItems`、`MaxPreviewChars` 六个字段，但**全项目没有任何一行代码读它们** ——
> 面板上看着像开关，改了没反应。已在本版删掉，面板上剩下的每一个都是真的生效的。

### 二、插件窗口里的设置

- **装配页控制栏**：覆盖方式、启用 Handlebars 宏、自动宏应用、自动读取全文。
  - **自动宏应用**（默认开）：本插件没有酒馆那么丰富的宏能力，没实现也没定义的宏
    （`{{lastPrompt}}` 之类）直接**填成宏名本身**，预览里不再堆一长串「未识别的宏」；
    `{{char}}` 仍取角色名。
  - **自动读取全文**（默认开）：长正文不会一次性挤进报文，而是打开页面后在后台**逐条读回**，
    不用手动点「读取全文」。嫌它一直读可以关掉，回到「点了才读」。
- **宏设置**：填 `{{user}}` 的取值、补充自定义宏、查看可用宏清单。
- **酒馆兼容 → 导入选项**：导入角色卡时遇到卡内世界书怎么办 —— `每次询问` / `总是导入` / `从不导入`，
  存在 `Storage/ContextManager/ImportOptions.json`。

## 数据放在哪

都在角色的存储目录下：

```
Storage/ContextManager/
  Plans/<角色>.json                     装配计划
  CharacterPresets/<角色>.json          自动快照（应用/保存方案时自动更新）
  CharacterPresets/<角色>__<名称>.json   手动保存的命名快照
  Presets/<名>.json                     酒馆预设
  ImportOptions.json                    导入策略
  OverrideState/                        本地覆盖前的原始设定备份
```

装配计划丢了也能用自动快照恢复，所以插件一启用就能直接生效。

## 与酒馆（SillyTavern）的对应关系

支持 JSON V1/V2/V3 常用卡字段、PNG `chara`/`ccv3` 文本块，保留原始卡数据；
支持 `prompts` / `prompt_order` 的顺序与开关、常用角色字段、独立 JSON 世界书与 `character_book`
（关键词、常驻、次级关键词、大小写、插入顺序）；支持 `{{char}}` `{{user}}` `description` /
`personality` / `scenario` / `system` / `mesExamples` 等常用宏、三花括号、嵌套 `#if`/`#unless`/`else`、
`trim`、`noop`、`setvar`/`getvar`，以及 `{{!注释}}` 与 `{{//注释}}`。

**多条开场白**（`alternate_greetings`）会全部读出来，编号成「开场白 / 开场白 2 / 开场白 3 …」，
导入角色卡时每条单独成一个模块，勾你想用的那条即可；对应宏 `{{greeting}}`、`{{greeting2}}`…
以及 `{{alternateGreetings}}`、`{{greetingCount}}`。

**不等于**完整 SillyTavern 运行时：不执行扩展脚本、STscript、自定义 Handlebars helper、
`each`/`with`、正则扩展、概率触发 / 递归扫描、CharX。

## 已知边界

- **一次请求能装的内容有硬上限**。IPC 桥是 Socket.IO，单条报文超过 1 MB 会被 `413` 断开且两端都不重连
  ——那一次就是整程序卡死只能重启。所以长正文会分页 / 按需读取：
  全部正文加起来在约 **7.6 万字**以内可以一次全给；超出的部分由界面标出「预览」并提供「读取全文」，
  保存时后端按 Id 从磁盘回填原文，**不会丢内容**。
- 角色卡字段为空但设定全写在开场白里的「特殊卡」按**基本信息**导入（8 个可用字段：酒馆标准 6 个 +
  开场白 + 作者注释）。
- 世界书在每次请求时扫描最近若干条非 system 消息（默认 10 条），属于前置区域，
  不模拟酒馆的 depth / position 插入。
- **长时间运行不会越用越胀**（开一整天、插件覆盖一直挂着也没问题）：
  出站队列有界（256 条，满则丢新而不是无限堆积），窗口 / 定时器 / 请求前重组的委托都在
  关窗、停用角色、卸载插件时逐个释放；`state` 每次都是整份替换，旧对象直接可回收。
  **显存占用恒定** —— 界面全程是 DOM/CSS，没有任何 WebGL / canvas / video，
  显存只有那一个窗口的合成开销，不随会话变长而增长。
  两份诊断日志也都封顶：后端 `Storage/ContextManager/trace.log` 600 KB、
  前端 `renderer-trace.log` 512 KB，写满就只保留后半段。

## 开发

- 插件由 Alife 在运行时**热编译**：`Alife.PluginContext` 会直接编译插件目录下的所有 `.cs`，
  所以发布包里只有源码，**没有也不需要** `.csproj`，更不需要手工拷 DLL。
- 版本号有四处需要同步：`ContextManagerRuntime.AppBuild`、`app.js` 的 `APP_BUILD`、
  `index.html` 的 `?v=`，以及 `manifest.json` 的 `Version`。
